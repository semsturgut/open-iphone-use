# HID backend audit — 2026-10-26

This audit compares the shared macOS headless radio with `BLEHIDPeripheral.swift`,
and inspects the BlueZ and WinRT publishers. Şems reported that changing the macOS
headless service UUID from `1812` to `00001812-0000-1000-8000-00805F9B34FB`
changed startup from `servicePublishFailed` to `advertising` on his Mac. That fix
is retained. Advertising does not establish successful iPhone pairing or input.

## Findings and changes

| Area | Finding / action |
| --- | --- |
| Service UUID | macOS retains the full 128-bit spelling for publication and advertisement; regression checks reject the short spelling. BlueZ and WinRT already expand service, characteristic and descriptor UUIDs to the Bluetooth Base UUID. No arbitrary replacement service is used. |
| Report map | Headless macOS directly reads `BLEHIDPeripheral.reportDescriptor`. The Python map is byte-for-byte checked against that descriptor. All backends expose keyboard report 1 (8 bytes) and relative mouse report 2 (4 bytes), with input report-reference descriptors; notification payloads exclude the report ID. No Boot reports or LED output report are advertised. |
| macOS encrypted reads | Apple documents that a cached characteristic value sets readable properties/permissions. HID information and report map now use dynamic `nil` values with encrypted-read permissions in both Swift publishers; their read handlers return the same bytes as before. Input reports were already dynamic and require encrypted notifications. |
| macOS write handling | Headless writes now validate zero offset, HID control values 0/1 and report protocol value 1. A batch receives one response using its first request, as required by CoreBluetooth. Boot protocol is rejected. In-flight sends recheck subscription after backpressure waits. |
| Linux notifications | `encrypt-read`, `encrypt-write` and `encrypt-notify` are retained; BlueZ builds the CCC descriptor. `AcquireNotify` remains the targeted path. The fallback `Value` broadcast now rejects a second connected/paired phone on the adapter even if it has not read a characteristic yet. One phone per adapter is required for shared-notify fallback. Writes reject nonzero offsets. |
| Windows requests | WinRT already publishes full UUIDs with encrypted characteristic access and encrypted report references; CCC descriptors are generated by Windows. Writes now reject offsets and never send a protocol-error response to a write-without-response command. Startup diagnostics no longer claim every `DisabledByPolicy` result requires an administrator policy change. |

## Platform restrictions and behavior differences

- **macOS:** both publishers advertise the local name `Open iPhone Use` and HID service
  UUID by default. The legacy publisher can override the name; the shared radio uses
  the product name. CoreBluetooth's supported advertising keys are local name and
  service UUIDs; this code does not inject a GAP Appearance advertisement or publish
  OS-managed GAP/GATT services. The full HID UUID workaround is supported by the
  owner's reported advertising result, not a guarantee across macOS releases.
- **Linux:** BlueZ advertises a peripheral, full HID UUID and generic HID Appearance
  `0x03c0`, sets Pairable, and registers a `KeyboardDisplay` agent. Numeric comparison
  and other pairing approvals remain with the owner. Existing bonds stay in BlueZ's
  system store; this code does not clear them or auto-trust unknown devices. BlueZ's
  GATT database supports encrypted CCC writes through `encrypt-notify`. Registration
  errors are surfaced; no unencrypted fallback is substituted. Actual per-device
  `AcquireNotify` availability depends on the host BlueZ build.
- **Windows:** Microsoft's reserved-service list includes DIS, GATT, GAP and Scan
  Parameters, and does **not** list HID. This is not a claim that HID works on every
  adapter. The code checks peripheral-role support, service/characteristic creation
  results and advertising status. The OS controls the advertised friendly name,
  pairing prompts, bond store and generated descriptors. No reserved service or
  manually generated CCC descriptor is added. This minimal HID schema is not a
  claim of complete HOGP qualification (in particular, no application DIS is added).
- **Reconnect/restart:** the shared Mac service is republished, zero reports are read
  initially, and peers are rediscovered through report subscriptions. Bluetooth-off
  clears transient peers. Python saves device-to-peer/calibration bindings and checks
  current subscriptions; re-pairing with a changed identity requires fresh screen
  association. OS bonds are not recreated or removed automatically. The legacy
  native path uses a single central and a report queue; headless uses explicit
  per-central sends with a 3-second backpressure deadline. Neither OS acceptance nor
  a saved binding proves post-restart input delivery; owners may need to reconnect
  in AssistiveTouch and prepare with Safari visible (automatically on the first tile
  tap, or explicitly through CLI/MCP).
- **Timing:** portable control retains 8 ms motion spacing, 24 ms keyboard press/release
  spacing and 35 ms pointer presses (legacy native click: 30 ms). Shared Mac sends
  retry backpressure every 5 ms, preserving order through the serialized device
  action path. No unmeasured connection-interval tuning was introduced. iPhone
  acceleration, radio latency and simultaneous-device capacity remain hardware tests.

## Network changes

In automatic address/certificate mode, capture and CA-download sockets bind `0.0.0.0`.
An authenticated `/api/setup` read detects the current LAN IP, renews the leaf under the
same private CA, reloads the active TLS context, and updates `connection.json` and all
UI links. The UI polls setup every five seconds. Renewals are serialized and skipped
when the address is unchanged. Detection/renewal errors are shown instead of inventing
an address. The owner must reopen a new link and approve sharing; existing Safari
sessions and startup terminal text do not migrate. Explicit hosts and custom TLS
certificates remain fixed. Host firewall restrictions and a shared network still apply.

## Evidence

Regression checks cover the full macOS service UUID and shared descriptor, actual BlueZ
startup schemas with a fake D-Bus boundary, actual WinRT startup/write/notify methods
with fake projections, rejection of ambiguous broadcasts, and an authenticated address
change followed by a real TLS handshake on the existing listener for the new IP using
the original CA. Browser checks exercise invitation and tile-link updates.

These checks do not load WinRT on Windows, run a Linux radio, pair an iPhone, or verify a
physical tap. The owner's `advertising` result is recorded separately from our software
validation. Real pairing, encrypted subscriptions, taps, reconnect after helper restart,
and multiple physical phones still require owner testing.
